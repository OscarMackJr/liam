# Phase 02.1: Code Review Report

**Reviewed:** 2026-10-22
**Depth:** standard
**Status:** issues_found

## Summary

The strict URL validator in `src/config.rs` is sound. I traced these inputs and found no bypass:
- Port segment: `+5`, leading zeros, port 0, 65536 and above, empty, whitespace and unicode digits are all rejected. `u16::parse` accepts a leading `+`, but the `format!("{port}") != segment` round-trip catches it.
- Prefix: scheme case and every non-`127.0.0.1` host form fail the exact `http://127.0.0.1:` prefix. Userinfo and `@` fail because the port segment will not parse.
- Query and fragment: `?` and `#` anywhere are rejected.
- Route: trailing slash, double slash, percent-encoding, `..` and suffixes fail the exact `remainder != route` compare.

The other checks also hold:
- **Ordering:** all form checks run before the record is read. The port compare runs right after `validate_startup`, still before `Evidence::new` and before the client is built, so no path reaches the network early.
- **Content-free reasons:** failure reasons are `&'static str` and never carry the URL or port. Client errors are mapped with `map_err(|_| ..)`, so reqwest errors (which embed the URL) never reach stderr or evidence.
- **Endpoint joins:** `format!("{}/v1/...", base.trim_end_matches('/'))` onto a validated slash-free base is correct.
- **Proxy variables:** `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` are no longer read in `src`. `static_contract.rs` guards this, and `proxy_env_vars_are_ignored` covers it end to end.
- **Stubs gating:** `stubs` and the `LIAM_STUBS`/`LIAM_STUB_PID` overrides are all behind `cfg(feature = "stubs")`.

## Warnings

### WR-01: Validator unit tests do not pin the `+` sign, unicode-digit and whitespace port cases

**File:** `src/config.rs:~176-200`
**Issue:** The rejection table covers `05`, `0`, `70000`, `abc` and an empty port. It has no `+50413`, fullwidth or Arabic-indic digits, a space in the port, a trailing newline, or `@` in the port segment. `+50413` is the only one accepted by `str::parse::<u16>()`. It is rejected only by the `format!("{port}") != segment` round-trip, and no test fails if that guard is removed or simplified. The spec names these classes as the bypass-prone ones.
**Fix:** Add to `rejects_non_loopback_service_urls`:
```rust
"http://127.0.0.1:+50413/svc/hometown",
"http://127.0.0.1: 50413/svc/hometown",
"http://127.0.0.1:50413\n/svc/hometown",
"http://127.0.0.1:５０４１３/svc/hometown",
"http://127.0.0.1:50413@evil/svc/hometown",
```
Add `"http://127.0.0.1:50413/svc/hometown\n"` and `"http://127.0.0.1:50413/SVC/hometown"` to the wrong-route table.

## Info

### IN-01: Non-UTF-8 env value is reported as "missing"

**File:** `src/main.rs:144-153`
**Issue:** `env::var(..).unwrap_or_default()` maps `VarError::NotUnicode` to an empty string, so a present-but-invalid value gives `env:service_url_missing`. The spec says `service_url_missing` means absent or empty. It still fails closed and is content-free.
**Fix:** Use `env::var_os` and return `env:service_url_not_loopback` for non-Unicode values.

### IN-02: Stale names and misleading failure reason after the proxy removal

**File:** `src/clients/mod.rs`, `src/main.rs:~191`
**Issue:** `build_proxy_client` and `ProxyClient` no longer have a proxy; they are now the no-proxy service client. A client build failure is still reported as `hometown:unavailable` with exit 21, which is a misleading reason for what is a local setup failure. This is pre-existing behaviour.
**Fix:** Rename to `build_service_client`/`ServiceClient`. Consider an exit-11 reason such as `env:client_build`.

### IN-03: Stub helpers keep an ignored `path` parameter

**File:** `src/stubs.rs:~135-146`
**Issue:** `CaptureProxy::forward_once` and `forward_two_to` accept `_path` but ignore it, and `route_path` maps both services to the same base. Callers can believe they are constraining the route when they are not. This is stub-only code behind the `stubs` feature.
**Fix:** Drop the parameter and update the callers, or assert the expected path in the routing closure.
